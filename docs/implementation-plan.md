# Implementation Plan — Puck Editor Pipeline

## Context

The Puck visual editor and all supporting infrastructure will live inside `eNigma-TemplateFrontend` — the same project that contains the components. This eliminates cross-project code sharing, routing mismatches, Tailwind theme drift, and dependency copying.

Three existing documents define the foundation:

| Document | Defines |
|----------|---------|
| `docs/standards.md` | The binding contract between View components and the config generation script |
| `docs/automated-component-conversion.md` | The end-to-end pipeline overview |
| `docs/AST-PARSER.md` | The AST parser that converts existing `page.tsx` files into Puck seed JSON |

This document defines the concrete implementation steps, execution order, and verification criteria.

## Phase 1 — Foundation

Everything else blocks on these three steps.

### Step 1.1: Add `puckComponentName` to the standard

**Problem:** The AST parser outputs `"type": "PromotionBanner"` — the component name as it appears in `page.tsx` JSX. The config script would derive `"PromotionBannerView"` from the filename. These don't match. Puck's `Render` can't resolve the component.

**Solution:** Add a fifth required export to `docs/standards.md`:

```tsx
export const puckComponentName = "PromotionBanner";
```

The config script uses `puckComponentName` as the config key instead of deriving from the filename. This creates the three-way link:

```
page.tsx: <PromotionBanner ...>
                ↕ must match
seed JSON: { "type": "PromotionBanner", ... }
                ↕ must match
config: { "PromotionBanner": { render: PromotionBannerView, ... } }
```

**Also add optional sixth export for seed placeholders:**

```tsx
export const puckSeedData = {
  // Placeholder data for props the AST parser strips (data props)
  // Used by the seed post-processor to fill in stripped arrays
};
```

**Files to modify:**
- `docs/standards.md` — add `puckComponentName` to required exports, `puckSeedData` to optional exports
- `docs/automated-component-conversion.md` — update the script contract section

### Step 1.2: Fix the AST parser

**File:** `eNigma-TemplateFrontend/ast-parser.ts`

**Fix A — identifier leak (line 64-66):**

```ts
// Current (buggy)
if (t.isIdentifier(node)) {
  if (DATA_PROPS.has(node.name)) return '__DATA_PROP__';
  return node.name;  // ← returns "featuredCollection" as a string value
}

// Fixed
if (t.isIdentifier(node)) {
  return '__DATA_PROP__';  // unknown identifiers are runtime data, skip
}
```

**Fix B — drop the hardcoded `DATA_PROPS` blocklist:**

Invert the logic. Only resolve member expressions rooted in known content scope (`homepage`, `common`, `siteContent`). Everything else is runtime data:

```ts
function resolveExpression(node: t.Expression): unknown {
  if (t.isStringLiteral(node))  return node.value;
  if (t.isNumericLiteral(node)) return node.value;
  if (t.isBooleanLiteral(node)) return node.value;
  if (t.isNullLiteral(node))    return null;

  if (t.isMemberExpression(node)) {
    const root = getRootIdentifier(node);
    if (root === 'homepage' || root === 'common' || root === 'siteContent') {
      return resolveMemberExpression(node);
    }
    return '__DATA_PROP__';
  }

  // Identifiers, call expressions, conditional expressions = runtime data
  return '__DATA_PROP__';
}

function getRootIdentifier(node: t.MemberExpression): string | null {
  let current: t.Expression = node;
  while (t.isMemberExpression(current)) {
    current = current.object as t.Expression;
  }
  if (t.isIdentifier(current)) return current.name;
  return null;
}
```

**Fix C — add seed post-processing:**

After generating the raw JSON, merge `puckSeedData` from View files into sections that have stripped data props:

```ts
// For each section in the output JSON:
//   1. Find the View file with puckComponentName matching section.type
//   2. If the View exports puckSeedData, merge it into section.props
//   3. Existing props from siteContent are not overwritten
```

This requires the parser to know about View files. Either:
- Import all View files at the top of the script and build a lookup map
- Or: split into two scripts — parser produces raw JSON, post-processor merges seed data

**Verification:**
- Re-run parser on `app/page.tsx`
- Output JSON should have no identifier strings as prop values (no `"featuredCollection"`)
- Output JSON should have placeholder arrays for `CategoryHighlights.categories`, `FeaturedProductsGrid.products`, etc.
- Output JSON should still have correct siteContent values for content props

### Step 1.3: Write the config generation script

**File:** `scripts/generate-puck-config.ts`

**Logic:**

```
1. Glob for all *.tsx files under components/
2. For each file:
   a. Dynamic import
   b. Check if `puckFields` is exported
   c. If no → skip (not a Puck component)
   d. If yes → read all metadata exports:
      - puckComponentName (required) → config key
      - puckLabel (required) → drawer display name
      - puckCategory (required) → drawer grouping
      - puckFields (required) → field definitions
      - puckDefaults (required) → default props
   e. Find the component export:
      - Default export → use that
      - No default → named export matching filename without "View" suffix
   f. Assemble config entry:
      {
        [puckComponentName]: {
          category: puckCategory,
          label: puckLabel,
          fields: puckFields,
          defaultProps: puckDefaults,
          render: (props) => <Component {...props} />,
        }
      }
3. Combine all entries into one config object
4. Write to lib/puck-components.jsx
5. Log: included count, skipped count, any warnings
```

**Output format (`lib/puck-components.jsx`):**

```jsx
// AUTO-GENERATED by scripts/generate-puck-config.ts
// Do not edit manually — run "npm run generate:puck-config" to regenerate

import PromotionBannerView from "@/components/home/PromotionBannerView";
import HeroSectionView from "@/components/home/HeroSectionView";
// ...

const config = {
  PromotionBanner: {
    category: "Marketing",
    label: "Promotion Banner",
    fields: { ... },
    defaultProps: { ... },
    render: (props) => <PromotionBannerView {...props} />,
  },
  HeroSection: {
    category: "Home",
    label: "Hero Section",
    fields: { ... },
    defaultProps: { ... },
    render: (props) => <HeroSectionView {...props} />,
  },
  // ...
};

export default config;
```

**Add to `package.json`:**
```json
"generate:puck-config": "tsx scripts/generate-puck-config.ts"
```

**Verification:**
- Run script with 0 standardized components → outputs empty config, logs 0 included
- Run script with 1 standardized component → outputs config with 1 entry
- Config key matches `puckComponentName`, not filename
- `render` function is a simple spread (no adapter logic)

### Step 2.2: Build the seed JSON loading mechanism

Add a fallback chain to the editor:

```
Editor loads slug "home"
  │
  ├── GET /api/pages/home → 200? Use saved data (user has edited before)
  │
  └── 404? Load seed file
        │
        ├── data/seeds/home.json exists? Use as initial data
        │
        └── No seed? Start with { content: [] } (blank canvas)
```

**Implementation:**

1. Create `data/seeds/` directory in eNigma
2. Move `puck-homepage-default.json` to `data/seeds/home.json`
3. Update `lib/page-data.ts` — if no saved page exists, check for a seed file
4. The editor loads with pre-populated content on first visit, blank on subsequent visits if the user clears it

### Step 2.3: Handle data-stripped sections

```tsx

    { name: "Outerwear", slug: "outerwear", image: "https://...", itemCount: 42 },

The seed post-processor (from Step 1.2 Fix C) reads `puckSeedData` for each component type and merges it into the seed JSON where the AST parser stripped data props. Existing props from siteContent are not overwritten.

## Phase 3 — Hardening

After the pipeline is proven with the homepage.

### Step 3.1: Add validation tooling

**File:** `scripts/validate-puck-components.ts`

For each file exporting `puckFields`:

1. All five required exports present (`puckComponentName`, `puckLabel`, `puckCategory`, `puckFields`, `puckDefaults`)
2. Every key in `puckFields` exists in `puckDefaults`
3. `puckComponentName` is a non-empty string
4. No duplicate `puckComponentName` values across files
5. Select fields have `options` arrays
6. Array fields have `arrayFields` and `defaultItemProps`
7. If `puckSeedData` is exported, its keys don't overlap with `puckFields` keys (seed data fills gaps, not editable fields)

Run with: `npm run validate:puck`

### Step 3.2: Standardize remaining display components

After the 9 homepage components work, process the remaining ~35-40 display components across all folders.

### Step 3.3: Generate seed JSON for other pages

Once the config has components from multiple folders, run the AST parser on other eNigma pages:

```
app/page.tsx              → data/seeds/home.json
app/categories/[slug]/page.tsx → data/seeds/category.json
app/products/[slug]/page.tsx   → data/seeds/product.json

Each seed JSON references component types that must exist in the config. If a page uses a component that hasn't been standardized yet, the editor shows that section as unresolvable (Puck handles this gracefully — it renders nothing for unknown types).

## Verification Checklist (Per Component)

For each component entering the pipeline:

- [ ] View accepts only flat scalar props (string, number, boolean, arrays of flat objects)
- [ ] View contains no business logic (no date checks, no API calls, no store reads)
- [ ] View exports `puckComponentName`, `puckLabel`, `puckCategory`, `puckFields`, `puckDefaults`
- [ ] `puckComponentName` matches the component name used in `page.tsx` JSX
- [ ] Every key in `puckFields` has a matching prop in the View's interface
- [ ] Every key in `puckDefaults` has a matching key in `puckFields`
- [ ] Select fields for booleans use `"true"` / `"false"` string values
- [ ] Container (if present) preserves its original interface for existing routes
- [ ] Container delegates to View with flat props matching the View's interface
- [ ] If component has data props stripped by AST parser, `puckSeedData` provides placeholders
- [ ] `puckSeedData` keys don't overlap with `puckFields` keys
- [ ] Config script runs without warnings for this component
- [ ] Component appears in Puck editor drawer with correct label and category
- [ ] Component renders correctly when dragged onto canvas with defaults
- [ ] Component renders correctly on `/puck/[slug]` after publish
