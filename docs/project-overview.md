# dnd-test Project Overview

## What It Is

`dnd-test` is the Puck integration testbed for
`eNigma-TemplateFrontend`, the production Next.js storefront. Its purpose is to
turn real TemplateFrontend pages into editable Puck seed JSON, let authors edit
those pages in Puck, and publish pages that retain the original storefront's
visual structure and runtime behavior.

It is not intended to become a separate replacement storefront. It is the
proving ground for Puck-compatible components, parser behavior, seed generation,
and published-page rendering before the work is migrated into
`eNigma-TemplateFrontend`.

## Main Flow

1. `scripts/templatefrontend-parser/ast-parser.ts` reads a real
   TemplateFrontend source route and writes Puck seed JSON into
   `dnd-test/data/seeds`.
2. Puck loads the seed in `/editor?slug=<page-slug>` using the generated Puck
   component configuration and manifest.
3. Editors rearrange or edit supported components and slots.
4. `dnd-test` renders the saved seed at `/page/<slug>` (and supported dynamic
   nested routes), using route metadata and production-compatible API services.
5. Parser diagnostics and route-specific parity checks identify unmapped source
   JSX, unsupported conditions, unknown Puck types, or unsafe fallbacks.

## Repository Map

### Root Files

- `package.json` and `package-lock.json`: application dependencies and all
  parser, seed, typecheck, and parity-check commands.
- `next.config.ts`, `tailwind.config.ts`, `postcss.config.mjs`, and
  `eslint.config.mjs`: Next.js, styling, and lint configuration.
- `tsconfig.json`: the base TypeScript configuration.
- `tsconfig.typecheck.json`: the repository-wide typecheck input used by
  `npm run typecheck`.
- `auth.ts`: the testbed authentication configuration and session boundary.
- `.env.local`: local-only environment values. It must never be committed.
- `AGENTS.md` and `CLAUDE.md`: local agent guidance. They are not runtime code.

### Application Routes: `app/`

- `editor/`: the Puck editor. It loads a page by seed slug, saves to
  `data/pages.json`, and provides the View Page mapping.
- `page/[slug]/`: generic published Puck rendering for routes such as
  `/page/home` and `/page/products`.
- `page/[slug]/[entitySlug]/`: generic entity-aware Puck rendering where a
  generic published route is still appropriate.
- `products/`, `categories/`, `collections/`, `cart/`, `checkout/`, `search/`,
  `downloads/`, `wishlist/`, `auth/`, and `account/`: native URL bridges that
  preserve the real storefront URLs while rendering the matching Puck page.
- `api/pages/`: editor persistence endpoints for saved page data.
- `api/backend/[...path]/`: backend proxy used by the testbed API services.

### Component Layers

- `components/`: Puck-compatible component Views, fields, defaults, fetchers,
  and canonical renderers.
- `components/<domain>/canonical/`: source-faithful page regions and thin
  `*View` adapters. These are the preferred parser targets for nested page
  structures.
- `components/products/`, `components/categories/`, `components/search/`, and
  other domain folders: shared Puck leaves and route-specific runtime helpers.
- `components/ui/` and `components/layout/`: reusable visual primitives and
  small layout helpers.
- `enigma-components/`: production-compatible component copies/delegates.
  Puck Views use them when the original component behavior or DOM must be kept.
  This folder is currently required by DnD Test; it is not an unused archive.

### Runtime And Puck Infrastructure: `lib/`

- `api/`: typed backend clients and service modules used by both published
  Puck components and direct route bridges.
- `auth/`, `hooks/`, `stores/`, `actions/`, and `analytics/`: client/runtime
  infrastructure copied or adapted from the production storefront.
- `utils/`: formatters, catalog helpers, route helpers, and e-commerce utility
  functions.
- `puck-components.jsx`: generated client Puck configuration used by the
  editor.
- `puck-components.server.jsx`: generated server Puck configuration used by
  published pages.
- `puck-ast-manifest.json`: generated component metadata used by the parser and
  seed validation.
- `puck-route-composition.json`: generated route/slot grammar used by parser
  QA. It is local generated output and is ignored by Git.

### Page Data: `data/`

- `seeds/*.json`: the 32 canonical parser-generated Puck seed files. These are
  source-controlled because they are the reproducible visual and structural
  baseline for each route.
- `pages.json`: saved editor data used by published pages. It currently mirrors
  the regenerated canonical seeds so all 32 routes can be tested immediately.
- `seeds/_reports/`: per-route parser diagnostics. These are regenerated by the
  parser and ignored by Git; `seeds:apply` requires a clean local report before
  it replaces a saved page.
- `parser-fixtures/`: generated parser-combination matrices. These are ignored
  by Git and can be recreated by the parser QA commands.

### Tooling And Documentation

- `scripts/generate-puck-config.ts`: discovers Puck metadata and generates the
  client/server configs, AST manifest, and route composition grammar.
- `scripts/templatefrontend-parser/`: the DnD-owned AST parser entry point,
  recursive JSX engine, and declarative route profiles. It loads the Puck
  manifest and route grammar from this repository while inspecting a chosen
  TemplateFrontend source root.
- `scripts/run-parser-to-dnd-test.ps1`: runs the DnD-owned parser for all
  supported TemplateFrontend source routes and writes seeds plus diagnostics
  into DnD Test. `-TemplateFrontendRoot` selects the source tree to inspect.
- `scripts/apply-seed-to-page.ts`: validates a clean seed/report/manifest and
  copies a seed into `data/pages.json`.
- `scripts/apply-all-seeds-to-pages.ts`: validates every current seed and
  replaces `data/pages.json` with the complete latest route set in one write.
- `scripts/check-*.ts`: source-parity, canonical-structure, parser-resolution,
  and published-page QA checks.
- `docs/`: project decisions, audits, testing guides, and route references.
  The generated published-page QA guide/report are ignored because they are
  reproducible outputs.
- `public/`: static Next.js assets. It currently contains the default starter
  SVG assets and no core Puck-specific asset pipeline.

### Local Generated Directories

- `.next/`: Next.js build and development cache; safe to delete and ignored.
- `node_modules/`: installed dependencies; can be recreated with `npm ci` and
  is ignored.
- `tsconfig.tsbuildinfo`: TypeScript incremental cache; ignored.
- `temporary-context/templatefrontend-preservation-2026-08-04/`: ignored local
  recovery snapshot of the pre-cleanup TemplateFrontend canonical-parser work.
  It includes the copied source tree, a binary patch for tracked edits, and a
  file manifest. The active parser does not depend on this snapshot.

## Current Canonical Coverage

All 32 routes in the latest TemplateFrontend source now have a canonical Puck seed, a parser route
mapping, and generated configuration support. The parser is expected to emit
known component types and nested slots rather than opaque page-replacement
components. Route-specific parity and parser-resolution scripts protect this
contract.

Visual verification is still an active responsibility. The current work is to
compare every editor and published page to its TemplateFrontend route, fix
layout defects in the shared production-compatible components, and ensure saved
pages are refreshed from the current generated seeds before testing.

## Useful Commands

```powershell
# Start the Puck testbed.
npm run dev

# Regenerate Puck configuration and the AST manifest after component metadata changes.
npm run generate:puck-config

# Parse TemplateFrontend routes into dnd-test seeds.
npm run seeds:parse-template

# Apply a clean generated seed to a saved editor/published page.
npm run seeds:apply -- product-detail

# Replace saved editor/published data with every clean current seed.
npm run seeds:apply-all

# Typecheck the complete testbed.
npm run typecheck

# Run canonical parity checks for completed slices.
npm run qa:catalog-parity
npm run qa:product-detail-parity
npm run qa:categories-page-parity
npm run qa:category-detail-parity
npm run qa:account-settings-parity
npm run qa:account-orders-parity
npm run qa:full-jsx-parser
```

## Important Boundaries

- Puck preview data exists only to make the editor understandable. Published
  pages must read the same backend data and route/search state as the real page.
- Runtime arrays, conditions, loading boundaries, empty states, and errors must
  stay in source-domain components; the parser must not convert them into fixed
  JSON repetitions or show both conditional branches unconditionally.
- Views are adapters, not redesigns. They should pass the original props to
  original or production-compatible components rather than recreate their DOM.
- Cart, checkout, authentication, payment, account, and order mutations still
  require the original production infrastructure for true functional parity.
  Testbed replacement stores or server actions are not a valid final solution.
- `/account/orders` is protected in published Puck rendering: an unauthenticated
  order-service response redirects to `/page/auth` with its Puck return URL.
  Real order data in the testbed still requires the future hosted-identity to
  backend-token bridge.
